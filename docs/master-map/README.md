# Twixy Master Map

제품의 단일 진실(master map): 비전 → 비즈니스 목표 → 로드맵 → 백로그 → 릴리스 계획 → 스프린트(Jira) → Product Increment.
웹 페이지와 영/한 docx가 전부 **하나의 데이터 파일**에서 생성된다.

## 구조

```
docs/master-map/
├── data/map.mjs      ← 단일 소스. 수정은 여기서만 한다 (영/한 병기)
├── web/index.html    ← 웹 뷰 (언어 토글, 필터, 파생 매트릭스)
├── build-docx.mjs    ← docx 생성기 (EN/KO 두 벌)
└── out/              ← docx 산출물 (빌드 결과, 커밋 안 해도 됨)
```

## 사용법

```bash
npm run map:web    # 웹 뷰 열기 (http://localhost:4980/web/)
npm run map:docx   # 공식 문서 필요할 때 docx 두 벌 생성 → out/
```

## 편집 규칙

- **수정은 `data/map.mjs`에서만.** 웹/문서를 직접 고치지 않는다 (웹은 읽기 전용 뷰).
- 사람이 읽는 문자열은 전부 `L(en, ko)` 병기. 상태는 `statuses` 키로만 쓴다.
- 백로그 항목의 `release` 필드를 바꾸면 릴리스 계획 매트릭스가, `goal`을 바꾸면 목표 연결이 자동으로 따라온다.
  스프린트 항목의 `link`는 백로그 `id`를 가리킨다 (`'chore'` = Feature로 승격하지 않는 일회성 작업).
- 커밋 컨벤션: `docs(map): <변경 요약>` — Jira 키가 있으면 포함 (예: `docs(map): TWIX-45 → R2 배정`).
- 스프린트 스냅샷(6·7장)을 갱신할 때는 `sprint.fetchedAt` 날짜도 같이 바꾼다.

## 호스팅

- 기본: 레포가 곧 배포다. `git pull` 후 `npm run map:web` — 팀원 각자 로컬에서 최신을 본다.
- 상시 URL이 필요해지면: 정적 파일 두 개(web/index.html + data/map.mjs)라 어디든 올라간다.
  서버 이관(TWIX-27~29) 완료 후 twixy.dev 서브경로에 올리는 것을 권장 (내부 로드맵이므로 공개 호스팅에는 올리지 말 것).

## 갱신일 규칙

- 초기 전수조사(2026-08)로 들어온 항목은 개별 날짜 없이 기준선 `2026-08` 하나로 표기한다 (`BASELINE`).
- 이후 추가/수정하는 항목에는 `updated: 'YYYY-MM-DD'` 를 개별로 찍는다 — 목표·백로그 표의 "갱신" 열에 나온다.

## 브랜치 표기 규칙

- 그 작업이 실제로 이뤄진 git 브랜치를 백로그/에픽 항목의 `branch` 에 적는다 — 4장·5.1절 표의 "브랜치" 열에 나온다.
- 진행 중이거나 앞으로 추가되는 항목은 **필수**. 과거 항목 중 브랜치를 확정할 수 없는 것은 비워둔다 (추측해서 적지 않는다).
- 병합 후 브랜치가 삭제돼도 이름은 그대로 남긴다 — 그 작업이 어디서 이뤄졌는지의 기록이기 때문.
